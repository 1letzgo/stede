## Build & verify

Layout since 09/2026: the Xcode project holds only the app shell (`stede/stedeApp.swift`, `Info.plist`, entitlements, `Assets.xcassets` with AppIcon + AccentColor). All code lives in the local Swift package `Packages/Stede` with two targets: **StedeCore** (Models, Services, Support/{IslandTime,LoadState,FlexibleDecoding}, `Resources/*.json` — pure Foundation, no UI, everything the UI needs is `public`) and **StedeUI** (Views, ViewModels, StedeTheme, InAppBrowser, `Resources/Colors.xcassets` with the `Stede*` colorsets; `ContentView` is the only public entry). Resources load via `Bundle.module`, colours via `Color("StedeX", bundle: .module)`. Add new files under the matching `Sources/<Target>/` folder (SwiftPM picks them up; the Xcode project file stays untouched except for the package reference). Language mode Swift 5 with approachable concurrency features; StedeUI has `.defaultIsolation(MainActor.self)`, StedeCore is nonisolated by default. No CI, no lint config. Verification = compile:

```bash
xcodebuild -project stede.xcodeproj -scheme stede -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO
```

Parser tests (Swift Testing, fixtures under `Packages/Stede/Tests/StedeCoreTests/Fixtures`: city calendar HTML, dbf JSON, VBN XML, appfuhr PDF text). The build directory must lie outside the iCloud folder, otherwise SwiftPM's codesign step fails:

```bash
cd Packages/Stede && swift test --scratch-path /tmp/stede-spm --filter StedeCoreTests
```

Xcode 26.3; deployment targets 26.2 on iOS, macOS and visionOS (`SUPPORTED_PLATFORMS` includes xros). Keep code multiplatform: guard iOS-only APIs (`BackgroundTasks`, `UINavigationBar`, `.toolbar(for: .navigationBar)`) with `#if os(iOS)` / `#if !os(macOS)`.

## Critical project settings

- **Filesystem-synchronized project**: the app folder `stede/` is synced; sources live in the package. Never edit `project.pbxproj` to add files (only `Info.plist` is excluded via membership exception; the package is referenced as `XCLocalSwiftPackageReference Packages/Stede` with product `StedeUI`).
- **Default MainActor isolation** (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`): every type is MainActor-isolated unless marked `nonisolated`. Non-UI code (clients, models, support types) is explicitly `nonisolated` + `Sendable` — follow that convention or you hit Sendability errors.
- App Sandbox + hardened runtime on; `stede.entitlements` already has network-client. `Info.plist` only sets `ITSAppUsesNonExemptEncryption`; no background task, no StoreKit (all features are free).

## Architecture

Flow: `Views/` → `@Observable` ViewModels (`ViewModels/TabViewModels.swift`) → `*Store` (caching, `Services/`) → `*Client` (`Services/APIClients.swift`, pure fetch+parse, `nonisolated`).

- **IslandTime** (`Support/IslandTime.swift`): ALL day boundaries, formatting and timezone logic go through it (Europe/Berlin, de_DE). Never use `Calendar.current` or a default `DateFormatter` — the app shows island time regardless of device locale. Root locale is forced to `IslandTime.germanLocale` in `stedeApp`.
- **DayCache\<T\>** (`Services/DayCache.swift`): per-day JSON disk cache in Application Support (`<name>/YYYY-MM-DD.json`). New day-cached content needs its cache name registered in `CacheMaintenance.dayCacheNames` or it never gets purged (7-day retention).
- ViewModels use cache-then-network: show cached data immediately, refresh in background, keep stale data on error (`.failed` only when nothing is cached). `LoadState`/`AppError` live in `Support/LoadState.swift`; German error text via `AppError.errorDescription`.
- Each ViewModel exposes `load(day:force:)`; screens re-trigger it with `.task(id: openID)`, where `openID` is a fresh `UUID` handed down by `ContentView` on every tab switch. `SelectedDateStore` owns the selected day plus the `latestDate` upper bound; every day is free to browse.
- App start (`stedeApp`) purges expired caches and warms events/weather.

Comments (09/2026): `community_events.comments_enabled` (editor toggle „Kommentare erlauben“, only for internal events — switching to public turns it off) and table `event_comments` (body 1–1000 chars, FK to `profiles` for the name/avatar embed, cascades with event and user); RLS via `can_comment(event)` = comments enabled, visibility members, caller is an active member; insert only as oneself, delete own or as community admin/owner. Join requests carry an optional short introduction `community_members.join_message` (≤ 500 chars, asked in `JoinRequestSheet` / Android `JoinRequestDialog` only for approval groups, shown to admins via `JoinMessageText` in the group’s „Anfragen“ and in the Admin sheet; trigger `clear_join_message` empties it once the member becomes active). RLS: content readable by anyone, community internals only for active members, `tenant_admins` may only change `communities.status` — the App-Admin sees nothing inside a community unless they join. `bootstrap_admins` holds e-mail addresses that become tenant admin of every tenant on first login. **Wave 1 — content in the backend (09/2026).** Tables `places` (one row per place, `directory` gastro/health/leisure/sights/playgrounds/trips/bikes, `external_id` = the JSON id, soft delete via `deleted_at`, `status` review/published), `place_directories` (source + fetched_at per directory), `city_events` (one row per event occurrence, unique on tenant/external_id/day) and `job_runs`; anyone may read, only the service role writes. The bundle JSONs were uploaded once (generated SQL, 225 rows). Client: `ContentSync` (StedeCore) pulls per-directory deltas (`updated_at > cursor`) at app start into `Application Support/content/<directory>.json`; `GastroStore`/`BikeRentalStore` prefer that snapshot over the bundle (read once at launch — a fresh sync shows after the next start). `EventStore.events(on:)` asks `CityEventClient` (table `city_events`) first and falls back to the HTML scraper. Waste parsing (appfuhr PDF) stays client-side; see Wave 2 for the server path.

**Wave 2 — everything static or live goes through the backend (09/2026).** (1) The Ehrenamtskarte directory is in `places` (`volunteer`) like the other directories. (2) Static files live in the public bucket `content` (`<tenant>/bus-stops.json`, `abfuhr-strassen.json`, `inselkarte.json`) with one row per file in `content_files` (name, path, bytes, updated_at); `ContentFiles` (iOS StedeCore / Android `data/ContentFiles.kt`) downloads changed files at app start into `Application Support/content/files/` (Android `filesDir/content-files/`), and `BusStop.all`, `WasteStreetStore.directory`, `IslandMapData.shared` (Android `busStops`, `Waste.streets`, `OfflineMap`) prefer that copy over the bundle — effective from the next launch. To update a file: upload it to the bucket and bump `content_files.updated_at` (the one-off `content-import` function is retired, 410). (3) Live services run through Edge Functions with a server cache (`upstream_cache`, bytea, service role only, purged daily by cron `purge-upstream-cache`): `upstream?url=<encoded>` (no JWT; allowlist api.brightsky.dev/weather 30 min, dbf.finalrewind.org 60 s, fahrplaner.vbn.de/bin/stboard.exe 60 s; returns the upstream body unchanged, stale copy with `X-Stale` when the upstream fails) and `waste-calendar?street=&year=&section=&branch=` (runs the appfuhr makekal/makepdf/pdf flow server-side, caches the PDF 7 days). `HTTPClient.data(from:)` (Android `Http.text/bytes`) routes those hosts through `upstream` first and falls back to the direct request; `WasteClient` / `Waste.year` try `waste-calendar` first. Parsers stay in the apps.

## Data sources (unofficial public APIs)

**All POI directories are offline OpenStreetMap data (09/2026).** `Resources/gastronomie.json`, `sehenswuerdigkeiten.json`, `gesundheit.json`, `freizeit.json` and `fahrradverleih.json` were generated from one Overpass query over the Westerstede municipality (`area[admin_level=8][name=Westerstede]`, amenity/shop/healthcare/tourism/historic/leisure tags) by a throw-away Python script: names, addresses, phone, website and `opening_hours` (day names translated, `seasonNote` „Laut OpenStreetMap, nicht bestätigt“) come straight from OSM, teasers are short generated German lines („Restaurant in Westerstede-Ocholt – italienische Küche.“) or hand-written for the notable places, coordinates are the OSM node/centroid; places without `addr:*` tags got their street via Nominatim reverse geocoding (59 of them, 09/2026).
