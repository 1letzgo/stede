# AGENTS.md

SwiftUI app "Stede" (bundle `de.letzgo.stede`): town guide for Westerstede (Ammerland). Forked 09/2026 from the Langeoog app "Loog", Bahn (Westerstede-Ocholt), Kalender, Wetter, POIs and the offline map are Westerstede; only the air-quality station is still Langeoog. Ferry and tides were removed 09/2026. All user-facing strings and comments are **German**.

## Build & verify

- Layout since 09/2026: the Xcode project holds only the app shell (`stede/stedeApp.swift`, `Info.plist`, entitlements, `Assets.xcassets` with AppIcon + AccentColor). All code lives in the local Swift package `Packages/Stede` with two targets: **StedeCore** (Models, Services, Support/{IslandTime,LoadState,FlexibleDecoding}, `Resources/*.json` — pure Foundation, no UI, everything the UI needs is `public`) and **StedeUI** (Views, ViewModels, StedeTheme, InAppBrowser, `Resources/Colors.xcassets` with the `Stede*` colorsets; `ContentView` is the only public entry). Resources load via `Bundle.module`, colours via `Color("StedeX", bundle: .module)`. Add new files under the matching `Sources/<Target>/` folder (SwiftPM picks them up; the Xcode project file stays untouched except for the package reference). Language mode Swift 5 with approachable concurrency features; StedeUI has `.defaultIsolation(MainActor.self)`, StedeCore is nonisolated by default. No CI, no lint config. Verification = compile:
  ```
  xcodebuild -project stede.xcodeproj -scheme stede -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO
  ```
- Xcode 26.3; deployment targets 26.2 on iOS, macOS, and visionOS (`SUPPORTED_PLATFORMS` includes xros). Keep code multiplatform: guard iOS-only APIs (e.g. `BackgroundTasks`) with `#if os(iOS)`.

## Critical project settings

- **Filesystem-synchronized project**: the app folder `stede/` is synced; sources live in the package. Never edit `project.pbxproj` to add files (only `Info.plist` is excluded via membership exception; the package is referenced as `XCLocalSwiftPackageReference Packages/Stede` with product `StedeUI`).
- **Default MainActor isolation** (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`): every type is MainActor-isolated unless marked `nonisolated`. Non-UI code (clients, models, support types) is explicitly declared `nonisolated` + `Sendable` — follow that convention or you'll hit Sendability errors.
- App Sandbox + hardened runtime are on; `stede.entitlements` already has network-client. `Info.plist` only sets `ITSAppUsesNonExemptEncryption`; no background task, no StoreKit (all features are free).

## Architecture

Flow: `Views/` → `@Observable` ViewModels (`ViewModels/TabViewModels.swift`) → `*Store` (caching, `Services/`) → `*Client` (`Services/APIClients.swift`, pure fetch+parse, `nonisolated`).

- **IslandTime** (`Support/IslandTime.swift`): ALL day boundaries, formatting, and timezone logic must go through it (Europe/Berlin, de_DE). Never use `Calendar.current` or default `DateFormatter` — the app shows island time regardless of device locale. Root locale is forced to `de_DE` in `stedeApp`.
- **DayCache\<T\>** (`Services/DayCache.swift`): per-day JSON disk cache in Application Support (`<name>/YYYY-MM-DD.json`). New day-cached content needs a cache name registered in `CacheMaintenance.dayCacheNames` or it never gets purged (7-day retention).
- ViewModels use cache-then-network: show cached data immediately, refresh in background, keep stale data on error (`.failed` only when nothing cached). `LoadState`/`AppError` in `Support/LoadState.swift`; German error messages via `AppError.errorDescription`.
- **Design system** (`Support/StedeTheme.swift` + asset catalog): Westerstede palette derived from westerstede.de (09/2026: city logo petrol #294754 and rhododendron red #E30613, site petrol #294753, Stadtgrün #37AB49, orange #FF8A00, site blue #2E6EA5, warm greys #F1EFEE), role names kept from the island app: `StedeTheme.sand/surface/harborRed/duneGreen/sunAmber/seaTeal/deep/heather/mudflat` (light+dark colorsets `Stede*`) — bar/deep/ink = petrol #294753 (bar #1F3640 and ink #9FC3D0 in dark mode), harborRed = logo red #E30613, duneGreen = Stadtgrün #37AB49, sunAmber = orange #FF8A00, seaTeal = site blue #2E6EA5 (accent: time pills, highlighted cards, action chips, Bus), heather = rhododendron magenta, mudflat = warm brown; sand/surface #F1EFEE/#FFFFFF (dark #121719/#1E2528); accent `StedeTheme.iconBlue` and `AccentColor` are petrol #294753 (#9FC3D0 dark). Android `C` in `ui/Theme.kt` has the same values. The app icon is a light rhododendron blossom (#BCC3C6) on petrol #1F3640. `StedeTheme.deep` stays dark in both modes (filled chips); for text and symbols in that tone use `StedeTheme.ink` (petrol / light petrol in dark mode). Cards via `.stedeCard(highlighted:fill:)` with inner padding `StedeTheme.cardPadding` (16), one-line list cards via `.stedeRowCard()` (`rowPadding` 12/16); every page and every sheet gets the petrol bar via `.stedeBar()`, sheet forms/lists via `.stedeSheetForm()` (sand background); text fields inside cards are `StedeTextField` (sand capsule). Android mirrors these (`cardSurface`, `RowCard`, `StedeTextField`, petrol `SheetHeader`), icon tiles `StedeIconChip`, section headers `StedeSectionHeader` (system `.headline`, like Apple's own apps — no rounded design, no tracking). **Navigation** is fully native. `ContentView` is a `TabView(selection:)` with one `Tab` per `AppTab` (label = `AppTab.title`), each wrapping its screen in a `NavigationStack`. `TabScreen` (`Views/SharedViews.swift`) is the shared shell: it renders the content with `.refreshable` and drives the system navigation bar. The bar carries only the area name as the inline `title`. Day switching floats: `DayNavigator` is a Liquid Glass capsule (`glassEffect` in a `GlassEffectContainer`) overlaid just above the tab bar — chevron, the day („Heute" or „27. Aug. 2026") that opens `DatePickerSheet` (long-press jumps to today), chevron. `TabScreen` reserves `StedeTheme.SelectionRow.height` as bottom safe-area padding on every screen. `showsDateNavigator: false` (Start, Insel categories) omits the capsule. Wetter, Bahn and Bus are not tabs — Start pushes them with a `NavigationLink`, so they arrive with the system back button. Start tiles are `HomeTile` (tinted fill, 1 pt border in the area colour, large faded corner symbol, fixed `HomeTileMetrics.height` shared with the greeting card), grouped under `StedeSectionHeader` categories: „Unterwegs“ (Bahn, Bus), and „Stadt“: two large tiles side by side — „Entdecken“ (Sehenswürdigkeiten, Freizeit & Sport and — since 09/2026 — the Ausflüge, deduplicated by name; the separate Ausflüge tile is gone) and „Gastro“ (Restaurant, Café, Eiscafé, Imbiss, Bar in one filterable view) — then a row of four small tiles; formerly „Insel“ (built like Gastro: a large „Entdecken“ tile — Sehenswürdigkeiten plus the Freizeit & Sport facilities in one view — beside a row of Einkaufen (bakeries, drugstore and bike shops included), Spielplätze, Ausflüge and Gesundheit); „Externe Anbieter“/Strandkörbe were removed; within each section every tile has its own colour, and inside a category view every kind has its own colour and symbol too (pill, toggle, map pin — `IslandCatalog.color(for:)` / `symbol(for:)`); the greeting card on top doubles as the weather tile and pushes Wetter. Card action capsules use `StedeActionChip`. The tabs are Start, Kalender, Gruppen and Einstellungen; no in-app purchase. Einstellungen (`SettingsView` / Android `SettingsScreen`) holds the account row (pushes `AccountView(embedded: true)`, Android `AccountSheet`), street + sections, bus stop, train direction (same `@AppStorage` keys as the screens) and „Startseite anpassen“: section order, tile order within each section and per-tile visibility in `home.order` / `home.tiles` / `home.hidden` (the first two visible Stadt tiles render large; comma strings, `HomeLayout`/`HomeSection`/`HomeTileID`), honoured by `HomeView`/`StartScreen`; the Gruppen bar no longer has an account button. Every screen spaces its cards by `StedeTheme.cardSpacing`. Bahn's direction switch and the Gastro/Fahrradverleih filter pills use `.stedeSelectionChip(isSelected:)` capsules at the top of the content, sized to their chips, starting 16 pt below the bar like the first card elsewhere and `cardSpacing` above the list. The bar itself is petrol #294753 like the city logo (`StedeTheme.bar`, colorset `StedeBar`, #1F3640 in dark mode; Android `C.bar`): `.toolbarBackground(StedeTheme.bar, for: .navigationBar)` with `.toolbarBackgroundVisibility(.visible)` and `.toolbarColorScheme(.dark)`, so title, chevrons and the day button render white and the colour runs up into the status bar. Unlike the tab bar, which iOS 26 refuses to tint, the navigation bar takes the colour. The leading chevron group drops its glass capsule via `.sharedBackgroundVisibility(.hidden)`. Inside an `HStack` a `Divider()` renders vertically; use `Rectangle().fill(.separator).frame(height: 1)` for hairlines. Don't introduce ad-hoc colors; display numbers/titles use `.fontDesign(.rounded)`.

One Supabase project for all municipality apps: `https://fkzjlecsetbnumtqrnem.supabase.co` (EU-West, org letzgo). Publishable key and URL live in `StedeCore/Services/Backend.swift`; the app's tenant comes from `StedeTenantSlug` in `Info.plist` (`stede`). Schema and RLS are in the project's migration history (`community_schema`, `community_rls`, `security_hardening`, `bootstrap_tenant_admin`) — tables `tenants`, `tenant_admins`, `profiles` (trigger on `auth.users`), `communities` (status pending → approved/rejected by the tenant admin, archived by the owner), `community_members` (join trigger applies `join_policy`: open → active, approval → pending), `community_events` (visibility members/public, `published_at` set by trigger, `version` bumps on update), `event_participations`, `calendar_tokens`; storage buckets `event-photos`, `community-logos` and `avatars` (profile pictures, folder = own user id, path stored in `profiles.avatar_url`, shown via `PersonAvatar` instead of the person symbol; all backend images (event photos, logos, avatars) load through `RemoteImage`/`RemoteImageCache` (StedeUI/Support: memory `NSCache` plus `Caches/images/<sha256>`, paths are immutable UUIDs, files unused for 90 days are purged at launch) — never plain `AsyncImage`, whose `URLCache` is too small for photos; `delete-account` removes them); table `community_header_images` (Standardbilder per community: files in `event-photos/<community>/defaults/`, members read, community admins manage; events only reference them, so `deleteEventPhoto`/`deletePhoto` never delete `/defaults/` paths, and deleting a Standardbild clears `image_path` on events using it; editable under the ⚙︎ tab, pickable in the event editor; the six Westerstede templates came from SPD vor Ort); sharing an event (`EventShare` on iOS/Android: photo + text „Titel / Wann / Ort / Beschreibung / Community · geteilt aus der stede-App“ via the system share sheet, from the detail sheet or a long press on the card; Android shares the photo through a FileProvider `${applicationId}.share`); views `v_community_overview` (with `member_count`) and `v_public_events`. Comments (09/2026): `community_events.comments_enabled` (editor toggle „Kommentare erlauben“, only for internal events — switching to public turns it off) and table `event_comments` (body 1–1000 chars, FK to `profiles` for the name/avatar embed, cascades with event and user); RLS via `can_comment(event)` = comments enabled, visibility members, caller is an active member; insert only as oneself, delete own or as community admin/owner. UI: `EventCommentsSection` (iOS, in `CommunityEventDetailView`) / `EventComments` (Android, in `EventDetailSheet`), delete by long press. `shares_community()` also lets group owners/admins read the profiles of pending applicants, so membership requests show the display name. Join requests carry an optional short introduction `community_members.join_message` (≤ 500 chars, asked in `JoinRequestSheet` / Android `JoinRequestDialog` only for approval groups, shown to admins via `JoinMessageText` in the group’s „Anfragen“ and in the Admin sheet; trigger `clear_join_message` empties it once the member becomes active). RLS: content readable by anyone, community internals only for active members, `tenant_admins` may only change `communities.status` — the App-Admin sees nothing inside a community unless they join. `bootstrap_admins` holds e-mail addresses that become tenant admin of every tenant on first login. Edge Functions: `calendar-feed` (no JWT, token in URL: `/functions/v1/calendar-feed/<token>.ics?scope=mine|communities`) and `delete-account` (JWT, deletes the auth user, archives communities where the user was sole owner).

User-facing wording is „Gruppe/Gruppen“ (tab „Gruppen“, „Gruppe gründen“, calendar filter „Gruppen“) since 09/2026 — code, tables and file names keep `community`. Client side: `Models/Community.swift` (Codable rows, snake_case keys), `Services/CommunityClient.swift` (all PostgREST calls), `StedeUI/Community/` (`AuthStore` — session, profile, memberships, tenant admin flag; Sign in with Apple via `SignInWithAppleButton` + nonce, Magic Link with redirect `stede://auth-callback`; `CommunityListView`, `CommunityDetailView`, `EventEditorView`, `AdminView`, `AccountView`). `ContentView` injects `AuthStore`, adds the Community tab (the Admin screen opens as a sheet from a seal button in its bar, only for tenant admins or community owners/admins), and handles the auth deep link. `EventView` merges city events, own-community events and public community events (`CalendarEntry`). The Kalender tab is a continuous feed (`CalendarFeedModel` / Android `CalendarScreen`): it opens on today (range today−7 … today+20), loads the next 21 days automatically when the bottom spinner appears (up to a year ahead) and earlier 21-day pages via the „Frühere Termine“ chip at the top; „Heute“ in the bar scrolls back; only days with events are shown, plus today. City events come from one `city_events` range query per page (`EventStore.events(from:through:)` / `CityEvents.range`), which also fills the per-day cache; the week navigator is no longer used there. Manual dashboard steps still required: enable the Apple provider (Services ID, key) and add `stede://auth-callback` to the redirect allowlist under Authentication → URL Configuration; the Sign in with Apple capability must exist on the App ID.

**Wave 1 — content in the backend (09/2026).** Tables `places` (one row per place, `directory` gastro/health/leisure/sights/playgrounds/trips/bikes, `external_id` = the JSON id, soft delete via `deleted_at`, `status` review/published), `place_directories` (source + fetched_at per directory), `city_events` (one row per event occurrence, unique on tenant/external_id/day) and `job_runs`; anyone may read, only the service role writes. The bundle JSONs were uploaded once (generated SQL, 225 rows). Edge Function `sync-city-events` (JWT) scrapes the city's event search — URL template in `tenants.config.events_search_url` with `{from}`, `{to}`, `{page}` — for today+`days` (default 60; the cron job passes `?days=120`), upserts into `city_events` and soft-deletes vanished rows; `pg_cron` job `sync-city-events` calls `/sync-city-events?days=120` hourly (`7 * * * *`) via `pg_net` with the anon JWT. Client: `ContentSync` (StedeCore) pulls per-directory deltas (`updated_at > cursor`) at app start into `Application Support/content/<directory>.json`; `GastroStore`/`BikeRentalStore` prefer that snapshot over the bundle (read once at launch — a fresh sync shows after the next start). `EventStore.events(on:)` asks `CityEventClient` (table `city_events`) first and falls back to the HTML scraper. Waste parsing (appfuhr PDF) stays client-side; see Wave 2 for the server path.

**Wave 2 — everything static or live goes through the backend (09/2026).** (1) The Ehrenamtskarte directory is in `places` (`volunteer`) like the other directories. (2) Static files live in the public bucket `content` (`<tenant>/bus-stops.json`, `abfuhr-strassen.json`, `inselkarte.json`) with one row per file in `content_files` (name, path, bytes, updated_at); `ContentFiles` (iOS StedeCore / Android `data/ContentFiles.kt`) downloads changed files at app start into `Application Support/content/files/` (Android `filesDir/content-files/`), and `BusStop.all`, `WasteStreetStore.directory`, `IslandMapData.shared` (Android `busStops`, `Waste.streets`, `OfflineMap`) prefer that copy over the bundle — effective from the next launch. To update a file: upload it to the bucket and bump `content_files.updated_at` (the one-off `content-import` function is retired, 410). (3) Live services run through Edge Functions with a server cache (`upstream_cache`, bytea, service role only, purged daily by cron `purge-upstream-cache`): `upstream?url=<encoded>` (no JWT; allowlist api.brightsky.dev/weather 30 min, luftdaten.umweltbundesamt.de/api-proxy/airquality/json 30 min, dbf.finalrewind.org 60 s, fahrplaner.vbn.de/bin/stboard.exe 60 s; returns the upstream body unchanged, stale copy with `X-Stale` when the upstream fails) and `waste-calendar?street=&year=&section=&branch=` (runs the appfuhr makekal/makepdf/pdf flow server-side, caches the PDF 7 days). `HTTPClient.data(from:)` (Android `Http.text/bytes`) routes those hosts through `upstream` first and falls back to the direct request; `WasteClient` / `Waste.year` try `waste-calendar` first. Parsers stay in the apps.

## Data sources (unofficial public APIs)

**All POI directories are offline OpenStreetMap data (09/2026).** `Resources/gastronomie.json`, `sehenswuerdigkeiten.json`, `gesundheit.json`, `freizeit.json` and `fahrradverleih.json` were generated from one Overpass query over the Westerstede municipality (`area[admin_level=8][name=Westerstede]`, amenity/shop/healthcare/tourism/historic/leisure tags) by a throw-away Python script: names, addresses, phone, website and `opening_hours` (day names translated, `seasonNote` „Laut OpenStreetMap, nicht bestätigt“) come straight from OSM, teasers are short generated German lines („Restaurant in Westerstede-Ocholt – italienische Küche.“) or hand-written for the notable places, coordinates are the OSM node/centroid; places without `addr:*` tags got their street via Nominatim reverse geocoding (59 of them, 09/2026). No photos ship (`GastroPlace.imageURL` stays nil), no `detailURL`. Same `GastroDirectory` schema as before (`source`, `fetchedAt`, `places[]`). Contents: **Gastro** 103 places in Restaurant / Café / Eiscafé / Imbiss / Bar / Bäckerei / Einkaufen / Drogerie (Einkaufen holds supermarkets, kiosks, florists, garden centres, bookshops, farm shops); **Gesundheit** 29 in Allgemeinmedizin / Facharzt / Zahnarzt / Apotheke / Klinik (Ammerland-Klinik, Bundeswehrkrankenhaus) / Therapie & Pflege / Tierarzt, the view adds 112/116117 and the Ammerland-Klinik emergency room; **Freizeit & Sport** 25 in Bad (Hössen Schwimmbad) / Sport / Spiel & Familie / Kultur (Stadtbücherei, museums, Freilichtbühne Howiek, Apothekervilla); **Sehenswürdigkeiten** 25 (St.-Petri-Kirche, Rhododendronpark Hobbie, Schloss Fikensolt, Draisinen-Bahnhof, Stadtpark, show gardens, churches — war memorials and minor artworks filtered out); **Fahrrad** (`IslandCatalog.bikeCategory`, was Fahrradverleih) 4 bike shops with `features` Verleih / Werkstatt / Verkauf / Fahrradladen — they have no tile of their own any more but are appended to the „Einkaufen“ view as kind „Fahrrad“. **Spielplätze** (`spielplaetze.json`, `GastroStore.playgrounds`, `IslandCatalog.playgroundsCategory`, tile in the Stadt row): the 34 municipal playgrounds scraped from westerstede.de/leben/kinder/kinder-spielplaetze (name, street, Besonderheit, Sauberkeit, Kinderrat grade as `seasonNote`), geocoded once via Nominatim; kinds Spielplatz / Skaterplatz, plus hand-added paid venue LandErlebnis Janßen (kind „Kostenpflichtig“, also in the backend `places` table — the synced snapshot wins over the bundle, so new places must go there too). **Ausflüge** (`ausfluege.json`, 5, hand-written): Rhododendronpark Hobbie, Ammerland-Draisine, Park der Gärten, Zwischenahner Meer, Ammerländer Rhododendronroute with kinds Park / Draisine / Schifffahrt / Radtour. **Ehrenamtskarte** (tile/category name, was „Ehrenamt“; `ehrenamt.json`, `GastroStore.volunteer`, `IslandCatalog.volunteerCategory` / Android `Catalog.VOLUNTEER`, directory key `volunteer`, bundle only): the 12 Westerstede discounts of the Ehrenamtskarte Niedersachsen/Bremen from the Ammerland PDF `ehrenamtskarte-freiwilligenserver.de/htmlclient/OfficeGODownloads/Ammerland.pdf` (entries „Stadt Westerstede“), merged to 9 providers, geocoded via Nominatim, kinds Verwaltung / Bildung / Mobilität / Handel / Übernachtung / Versicherung; optional Stadt tile `HomeTileID.volunteer`, hidden by default (`HomeLayout.defaultHidden`), switchable in Einstellungen → Startseite. The live search behind freiwilligenserver.de posts JSON to `ehrenamtskarte-freiwilligenserver.de/Verguenstiger/VerguenstigerRabattliste` — re-check the PDF by hand when refreshing. Symbols and colours per kind live in `IslandCatalog.symbol(for:)` / `color(for:)`. To refresh: re-run the Overpass query and the conversion (filters for memorials, school halls, shooting clubs), then re-check the hand-written teasers.

**Offline-Stadtkarte** (`Views/OfflineIslandMap.swift`, data `Resources/inselkarte.json`, ~2.2 MB): `LoogPlaceMap`'s UIKit map draws a blank `MKTileOverlay` plus our own overlays from two Overpass extracts: the core bbox 53.19–53.28 N, 7.86–7.98 E (Kernstadt and Ocholt, with buildings and paths) merged with the whole municipality 53.17–53.35 N, 7.80–8.07 E (roads, rail, wood, water, settlement — every POI lies inside): `land` is the bbox rectangle, `polygons` settlement / green / wood / water, `buildings` (emptied 09/2026 — individual buildings are not drawn, the settlement area is enough; the file shrank from 2.6 to 1.4 MB), `lines` road / path / rail / stream (paths only drawn when zoomed in); the blank base tiles are opaque sand so MapKit never shows its grid placeholder; the overlays are built once per launch in `OfflineMapLayers.shared` (warmed up in the background by `ContentView`) and shared by every map view — do not rebuild them per view — Douglas-Peucker simplified, 5-decimal coordinates. Layer keys `tidalflat`, `sand`, `dune`, `saltmarsh`, `groyne` are no longer present in the data but still tolerated by the renderer. Since 09/2026 a third Overpass extract (bbox 53.15–53.26 N, 7.95–8.10 E, same classification, rings simplified in two halves) adds Bad Zwischenahn with the Zwischenahner Meer and Park der Gärten; `land` is now 53.15–53.35 N, 7.80–8.10 E. Camera boundary centre 53.25/7.95, span 0.20×0.30; default region in `PlaceBrowsing` centres on the Marktplatz (53.257/7.927). Re-run the extract by hand when the town changes.

**Bahn** (`Models/TrainDeparture.swift`, `TrainClient`, `TrainStore` — an actor holding the last board for 60 s, no DayCache): the departure monitor `dbf.finalrewind.org/Westerstede-Ocholt.json?version=3` (DB IRIS, open source). It knows only „now“ and roughly the next two hours (`lookahead` is ignored), so `TrainViewModel` shows `.empty` for any day but today. bahn.de's own board API (`www.bahn.de/web/api/reiseloesung/abfahrten`) answers 403 to the app, and bahn.expert's `POST /api/orpc/iris/departures` (`{"json":{"evaNumber":"8004610","lookahead":600,"lookbehind":10}}`) would be the alternative with a longer horizon. Times come as „HH:mm“ and are placed on today (after-midnight rows on tomorrow); the client merges the double listing of ICs with Nahverkehrsfreigabe (`RE IC56` + `IC 2034` → one row) and sorts trains into `TrainDirection` Oldenburg/Leer by the route stops after Westerstede-Ocholt. `TrainView` (pushed from Start via `HomeDestination.train`) has the direction switch on top; `ContentView` owns the selected direction and persists it via `@AppStorage("train.direction")` (`TrainDirection` is `String`-backed). **Bus** (`Models/BusDeparture.swift`, `BusClient`, `BusStore`, `BusView`, `HomeDestination.bus`): the VBN HAFAS board `fahrplaner.vbn.de/bin/stboard.exe/dn?L=vs_java3` (XML `<Journey …/>` rows) per stop id and day — 120 rows per call, the client pages by time until the day is covered, keeps only `prod` `#Bus`, `delay="-"` means no realtime. `BusStop.all` is a curated list of 22 Westerstede stops (ids from the VBN `ajax-getstop.exe` search, ZOB first); the chosen stop lives in `@AppStorage("bus.stop")`, read independently by `BusView` and `HomeView` (not passed through `ContentView`, which would re-render the whole TabView on every change), picked only in Einstellungen via `BusStopSheet` (a `List` sheet; no `Menu`/`Picker`: their labels redraw late) — `BusView` shows it in the bar title („Bus – ZOB“); today's list hides departures that have already left. Start shows Bahn and Bus side by side under „Unterwegs“, then a compact „Abfuhr“ tile under „Zuhause“ (next collection of the chosen street). **Abfuhr** (`Models/WasteCalendar.swift`, `WasteClient`/`WasteStore` in `Services/WasteStore.swift`, `WasteView`, `HomeDestination.waste`, Start section „Zuhause“): the Ammerland waste calendar via appfuhr.de, which only offers PDF export — the client calls `api/makekal.php?uid=<32 hex>&str=<street>&strgr=<section|null>&astgr=<branch|null>&komp=false&vier=false&jahr=<yy>&max=999`, then `pdf/makepdf.php?uuid=…&str=…&jahr=…&sw=false`, downloads `pdf/tmp/<uid>.pdf`, reads it with PDFKit and `WastePDFParser` turns lines like „Freitag, 2.1. Restabfall“ into `WasteCollection`s (kinds Restabfall / Papier / Gelber Sack / Bioabfall / Ast- und Strauchwerk / Problemstoffe). Results are cached per street+section+year in `Application Support/waste/<key>.json` (yearly data, never purged). The 548 Westerstede streets ship in `Resources/abfuhr-strassen.json` (from `api/json.php?tbl=str&ort=5`, 14 of them with `sections`/`branchSections` from `tbl=strgr`/`tbl=astgr`); the chosen street and sections live in `@AppStorage("waste.street"/"waste.section"/"waste.branchSection")`, wrapped by `WasteSettings` (StedeUI); street and sections are picked only in Einstellungen (`StreetSheet`), `WasteView` links to Einstellungen while nothing is chosen. Unofficial private service — re-check yearly, data is „Ende 2025“. **Kalender**: the city's event search `www.westerstede.de/regional/veranstaltungen/suche.html` (NOLIS-Manager, 15 hits per page, `p0` pages, `zeitauswahl=4` with `beginn_datum`/`ende_datum`), parsed by `EventHTMLParser` from the `terminanker_<id>` blocks (title, date/time incl. end time, Kurzbeschreibung, Veranstaltungsort, Veranstalter, Rubrik, series note, detail URL). Weather comes from Bright Sky for 53.256/7.927 (Westerstede). Weather `api.brightsky.dev`; the UBA air-quality proxy still uses the Langeoog station. These return inconsistent types — use `FlexibleDecoding.swift` helpers and `JSONDecoder.api` for dates. `HTTPClient` sets a Safari User-Agent (some endpoints require it).

## Android (`android/`)

Kotlin/Compose app with feature parity to iOS (09/2026), package `de.letzgo.stede`, same Supabase backend and tenant. Toolchain: `JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home`, `ANDROID_HOME=/opt/homebrew/share/android-commandlinetools`, AVD `stede`; build with `./gradlew assembleDebug` in `android/`; build output lives outside iCloud in `~/Library/Caches/stede-android/` (APK under `app/outputs/apk/debug/`), because iCloud sync broke the dex merge. `data/` mirrors StedeCore (Backend via supabase-kt, Places with `places` delta sync, CityEvents, Community API, Transit dbf/VBN, Weather/Air, Waste via appfuhr + pdfbox-android, file caches in `filesDir`, prefs keys identical to the iOS AppStorage keys); `ui/` mirrors StedeUI (Start, Wetter, Bahn, Bus, Abfuhr, category screens with Canvas offline map, week calendar with filters, Community list/detail/editors, Admin and Profil sheets). `MainActivity` holds three tabs with a back stack per tab (`Screen`) and handles the `stede://auth-callback` magic link. Bundle JSONs are copies in `app/src/main/assets/` — re-copy after regenerating them. Release: `./gradlew bundleRelease` (R8 + resource shrinking, rules in `app/proguard-rules.pro`; test the release APK, pdfbox and kotlinx.serialization rely on keep rules), compileSdk/targetSdk 36 (Play requirement), AGP 8.10.1. Signed with the upload key in `~/Library/Application Support/stede-signing/` (`upload.jks` + `keystore.properties`, never commit; without it the release build is unsigned); bump `versionCode` for every upload. Store material lives in `store/`: `play/listing.md` (texts and Play Console answers), `play/data-safety.md`, `play/screenshots/` (1080×2160, Play allows max. 2:1), `play/icon-512.png`, `play/feature-graphic.png`, and `datenschutz.html` (privacy policy, needs a public URL; placeholders for the controller). The launcher icon is the iOS app icon (light rhododendron blossom on petrol #1F3640, cropped at the bottom right, 09/2026) as adaptive icon: `res/drawable-nodpi/ic_launcher_back.png` is the whole icon scaled to the visible 72 dp and surrounded by flat petrol (not edge-extended — the blossom bleeds off the edge), foreground transparent, `ic_launcher_mono.png` the blossom lines only (monochrome/themed icons). Regenerate both, `store/play/icon-512.png` and `feature-graphic.png` from `stede/Assets.xcassets/AppIcon.appiconset/loog-3.png` when the iOS icon changes.
